# ТЗ: «Отладочный режим» сервера

Отдельный экран плеера для управления домашним сервером: состояние, буфер сети VLC,
загрузка и скачивание музыки, удаление.

Решения по интерфейсу и правилам — владельца (согласованы 2026-11-05), ниже они
зафиксированы. Внешний вид экрана — на усмотрение владельца, визуальные параметры
выносятся в `UI_config.txt`, новая секция `[UI server]`, как остальные.

---

## 1. Экран

- Открывается **поверх плеера** через `page.views` (второй `ft.View` поверх корневого),
  закрывается кнопкой «Назад» и `page.on_view_pop`. Отдельного окна Windows нет:
  Flet 0.85 не умеет открывать второе окно из того же процесса.
- Музыка продолжает играть: VLC, `bg_ui_process` и pubsub живут в том же процессе.
- Код — новый модуль `server_panel.py`, точка входа `open_server_panel(page)`.
  В `gui2.py` нужна только одна строка — вызов из кнопки владельца.

Разделы экрана: **Состояние** · **Буфер** · **Файлы** · **Операции**.

## 2. Права

| Действие | Кто |
|---|---|
| слушать, скачивать | все, у кого есть токен |
| загружать | все, у кого есть токен |
| откатить **свою** загрузку | тот, кто загрузил, **в любой момент** |
| удалить что угодно | только администраторы |

- `server.ini`, `[Server] admins = me` — имена из `[Tokens]` через запятую.
  Читается в `server/config.py` рядом с `tokens`.
- Имя и признак администратора даёт `user(request)` (`server/server.py`): `who_is()`
  плюс проверка по `cfg.admins`. Middleware `check_token` не меняется.
- Если в `[Tokens]` нет ни одной строки (сервер открыт), администраторов нет:
  удаление недоступно. Без токенов удалять мог бы любой в сети.
- Перезаписать существующий файл нельзя никому: это и есть «удалить существующее».
  Совпадение с уже лежащим файлом = пропуск с пометкой «уже есть».

## 3. Структура папок

Строго: **`Исполнитель/Альбом/трек`**, картинки — в папке альбома или в `covers/`.

| Что | Где разрешено | Пример |
|---|---|---|
| аудио (`SUPPORTED_FORMATS`: mp3, wav, flac, m4a, ogg, mp4) | глубина ровно 3 | `Muse/Origin of Symmetry/Bliss.flac` |
| картинки (jpg, jpeg, png, webp) | глубина 3 или 4 внутри `covers/` | `Muse/Origin of Symmetry/cover.jpg`, `…/covers/back.jpg` |
| всё остальное (`.txt`, `.cue`, `.log`, …) | нигде | — |

**Многодисковые альбомы.** Если внутри папки альбома есть подпапки с аудио (не `covers`),
их треки сливаются в саму папку альбома: `Альбом/CD1/x.flac` → `Альбом/x.flac`.
Номера дисков к именам **не добавляются**: у владельца префиксы вида `1 - ` и `1. `
обычно удалены из имён. Если после слияния два файла получают одно имя, в предпросмотре
пользователь **сам выбирает**, какой оставить.

**Имена:**
- сравниваются **без учёта регистра**: диск в NTFS, и в Windows `Bliss.flac` и `bliss.flac` — один файл;
- запрещены символы, недопустимые в Windows (`<>:"/\|?*`), и точка или пробел в конце имени.
  Иначе диск, подключённый к Windows, покажет битые имена.

**Уровень загрузки** зависит от открытой на сервере папки («в выбранную папку»):

| Открыта | Что выбирается на ПК |
|---|---|
| корень | папки исполнителей |
| исполнитель | папки альбомов |
| альбом | треки, картинки, папка `covers` |

Неподходящая глубина — ошибка в предпросмотре, а не молчаливая раскладка куда попало.

Правила проверяются **дважды**:
1. в плеере до загрузки — окно предпросмотра: что загрузится, что пропущено и почему, конфликты имён;
2. на сервере — для любого запроса. Нарушение = 400: клиент может быть старым или с ошибкой.

## 4. Сервер: новые эндпоинты

Все — в `server/server.py`, путь через существующий `safe_path()`.

| Запрос | Что делает |
|---|---|
| `GET /server/me` | `{"name": "sasha", "admin": false}` |
| `GET /server/ping` | +`disk_free`, `disk_total` (`shutil.disk_usage(cfg.root)`) |
| `GET /server/files?path=` | все разрешённые файлы под папкой, рекурсивно: `rel_path`, `size`, `kind` (audio/image). Нужен для скачивания: индекс знает только аудио, а `covers/` индексатор пропускает (`SKIP_DIRS` в `indexer.py`) |
| `GET /server/file?path=` | сам файл (аудио или картинка), `FileResponse` |
| `POST /server/ops` | начать операцию загрузки → `{"op_id": …}` |
| `PUT /server/file?path=&op=` | загрузить один файл, тело — байты файла потоком |
| `GET /server/ops?mine=1` | свои операции: когда, сколько файлов, откачена ли (администратор с `mine=0` видит все) |
| `GET /server/ops/{op_id}` | файлы операции: `rel_path`, `size`, `removed` |
| `POST /server/ops/{op_id}/undo` | откатить: удалить файлы этой операции (только своей) |
| `DELETE /server/file?path=` | удалить файл или папку целиком (только `admin`) |

**`PUT /server/file`, по порядку:**
1. операция неизвестна → 404, чужая → 403, уже откачена → 410;
2. проверка структуры и имени (§3), иначе 400;
3. существующие папки берутся с регистром диска (`uploads.resolve_ci`): «muse/…» попадёт в «Muse/»;
4. файл с таким именем уже есть (без учёта регистра) → 409;
5. нет `Content-Length` → 411; на диске меньше, чем `Content-Length` + 200 МБ запаса → 507;
6. запись в `<имя>.<8 hex>.part` потоком (`request.stream()`), кусками по 1 МБ через
   `anyio.to_thread`, чтобы не блокировать отдачу музыки другим слушателям;
7. запрос оборвался или пришло не столько байт → `.part` и созданные пустые папки удаляются;
8. всё дошло → под замком повторная проверка «уже есть» и переименование `.part` → настоящее имя,
   запись в журнал операций. Две одновременные загрузки одного пути: одна 200, другая 409.

`.part` индексатор и так не видит: расширения нет в `SUPPORTED_FORMATS`.
При старте сервера оставшиеся `.part` (после выключения посреди загрузки) удаляются в фоне.

**Журнал операций** — отдельная база `uploads.db` рядом с `library.db`, а не таблица
в ней: `library.db` бывает пересоздана (`library_uuid`), а история загрузок
при этом теряться не должна. Две таблицы: `ops(op_id, who, folder, created, undone)` и
`files(op_id, rel_path, size, mtime_ns, created, removed)`. Код — `server/uploads.py`.

**Откат** удаляет файл, только если `size` и `mtime` совпадают с журналом.
Если файл с тех пор заменили или переложили, он не трогается и попадает в отчёт.

**Удаление и откат:** после удаления файлов опустевшие папки альбома и исполнителя
тоже удаляются. Затем запускается `indexer.scan(cfg)` в фоне: треки получат `missing = 1`.

После загрузки тоже запускается `indexer.scan(cfg)`, неполный, — через 5 с после
последнего загруженного файла (`uploads.ScanScheduler`): альбом идёт по файлу, и скан
после каждого не нужен. Если в этот момент уже идёт другой скан — повтор через 30 с.

Откат можно вызвать повторно: он трогает только файлы, которые ещё не удалены.

## 5. Плеер: передача файлов

- Методы в `RemoteSource` (`sources.py`): `me()`, `list_files()`, `upload()`, `download()`,
  `delete()`, `undo()`, `ops()`. Через существующий `_get`, для PUT/POST/DELETE —
  такой же обёрткой с тем же заголовком токена.
- Таймаут: подключение — `SRV_TIMEOUT`, чтение — 60 с. 5 секунд обычного
  `SRV_TIMEOUT` не хватит на 50-мегабайтный FLAC через Tailscale.
- Передачи идут **по одной**, в фоновом потоке. Прогресс уходит в UI через pubsub,
  топик `transfer_progress`: файл, байты, всего.
- **Отмена** — `threading.Event`, проверяется на каждом куске:
  - загрузка: поток обрывается, сервер удаляет `.part`. Уже загруженные файлы
    операции остаются, и предлагается «Откатить всё»;
  - скачивание: недокачанный файл удаляется, скачанные остаются.
- Файлы выбираются через `ft.FilePicker` (`pick_files`, `get_directory_path`).
  В десктопном режиме он отдаёт локальные пути, данные читаются из файла и шлются
  потоком, в память целиком не грузятся.
- **Скачивание:** трек, альбом или исполнитель → выбранная локальная папка
  с той же структурой, включая `covers/`. Уже существующий локальный файл пропускается.

## 6. Буфер сети (`network_caching`)

Сейчас буфер задаётся один раз при создании VLC (`utils.create_player`,
`--network-caching`), поэтому меняется только после перезапуска.

**Применение на лету:** буфер передаётся опцией для каждого трека —
`player.set_mrl(mrl, f":network-caching={sources.SRV_CACHING}")`. Это два места:
`load_track` и повтор в `bg_ui_process` (`ui_utils.py`). Тогда новое значение
действует со следующего трека, без перезапуска. Для локальных файлов опция ничего не меняет.

**Сохранение** в `config.txt`: заменяется только строка `network_caching = …`
в `[Server]`, так же построчно, как в `build.ps1`. Через `configparser.write`
пропали бы все комментарии файла.

**Интерфейс:** ползунок 300–10000 мс (шаг 100) и кнопка «Подобрать».

**Подбор:**
1. время ответа — 5 запросов `/server/ping`, берётся максимум;
2. скорость — первые 2 МБ потока одного трека (`Range: bytes=0-2097151`),
   битрейт — из строки этого трека;
3. рекомендация (эвристика):
   - скорость < 2× битрейта → 8000 мс;
   - < 5× битрейта → 5000 мс;
   - иначе `max(1000, 3 × время ответа)`;
   - ограничение 300–10000, округление до 100.

Замеры показываются цифрами рядом с рекомендацией. Значение ставится только кнопкой «Применить».

## 7. Раздел «Состояние»

Онлайн или нет, время ответа, `tracks`, идёт ли сканирование (`scan_running`),
свободное место на HDD, «вы: sasha (администратор / пользователь)».
Кнопка «Пересканировать» → существующий `POST /server/rescan`.
