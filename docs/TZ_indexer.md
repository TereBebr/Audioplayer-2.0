# ТЗ: индексатор библиотеки на сервере

Дополнение к `TZ_streaming.md`, раздел 3.3. Описывает, что такое `library.db`, кто её
наполняет и в каком порядке это писать, прежде чем возвращаться к эндпоинтам.

---

## 0. Что это и зачем

Индексатор — это отдельный модуль на сервере, который обходит папку с музыкой, читает
теги каждого аудиофайла и складывает результат в SQLite-базу `library.db`. Всё, что
сервер потом отдаёт плееру — `id` трека, его название, длительность, обложка, поиск,
счётчик в ping — берётся **из этой базы, а не с диска**.

Диск читается только в двух случаях:
1. индексатор сканирует библиотеку (редко, в фоне);
2. `/api/stream/<id>` отдаёт байты файла (`FileResponse`).

Всё остальное — `SELECT`.

**`id` трека = `INTEGER PRIMARY KEY` строки в `tracks`.** Это и есть тот `track_id`,
который лежит в `srv://home/t/48213` на стороне плеера. Он назначается один раз при
первой индексации файла и больше никогда не меняется — ни при переименовании, ни при
переносе файла в другую папку, ни при перезапуске сервера.

## 1. Файлы

```
server/
├── server.py        # FastAPI, только HTTP: принял запрос → SELECT → отдал
├── db.py            # схема, get_conn(), init_db(), user_version
├── tags.py          # read_tags(path) -> dict: теги + тех. данные + байты обложки

├── server.ini       # конфиг (см. раздел 6)
├── library.db       # создаётся init_db()
└── covers/          # <sha1>_50.jpg, <sha1>_full.jpg
```

Разделение жёсткое: `server.py` не импортирует mutagen, `indexer.py` не импортирует
fastapi. Если хочется нарушить — значит, что-то лежит не в том файле.

## 2. Схема `library.db`

```sql
PRAGMA journal_mode = WAL;        -- сервер читает, пока индексатор пишет
PRAGMA user_version = 1;          -- версия схемы, проверяется на старте

CREATE TABLE tracks (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    rel_path    TEXT    NOT NULL UNIQUE,   -- 'Rock/Muse/Absolution/04 Hysteria.flac'
    dir         TEXT    NOT NULL,          -- 'Rock/Muse/Absolution'  (родитель rel_path)
    name        TEXT    NOT NULL,          -- из тегов, иначе имя файла без расширения
    author      TEXT,
    album       TEXT,
    year        TEXT,
    genre       TEXT,
    duration    REAL,                      -- секунды, число, не строка
    sample_rate INTEGER,
    bitrate     INTEGER,                   -- бит/с как отдаёт mutagen, делить на 1000 будет клиент
    channels    INTEGER,
    bits        INTEGER,                   -- глубина, NULL для mp3/ogg
    size        INTEGER NOT NULL,          -- байт
    mtime       INTEGER NOT NULL,          -- int(st_mtime)
    cover_hash  TEXT,                      -- sha1 байтов обложки; NULL = обложки нет
    seen_gen    INTEGER NOT NULL,          -- поколение скана, в котором файл видели последним
    missing     INTEGER NOT NULL DEFAULT 0 -- 1 = файла нет на диске, строка сохранена
);

CREATE INDEX idx_tracks_dir    ON tracks(dir);
CREATE INDEX idx_tracks_author ON tracks(author COLLATE NOCASE);
CREATE INDEX idx_tracks_album  ON tracks(album  COLLATE NOCASE);
CREATE INDEX idx_tracks_name   ON tracks(name   COLLATE NOCASE);

CREATE TABLE meta (
    key   TEXT PRIMARY KEY,
    value TEXT
);
-- ключи: scan_running (0/1), scan_gen, scan_started, scan_finished,
--        scan_seen, scan_parsed, scan_total_estimate, last_error
```

Почему именно так:

* **`rel_path` — всегда POSIX, через `Path.as_posix()`.** Ты разрабатываешь на Windows,
  а запускать будешь на Linux. Если в базу попадут обратные слэши, после переезда на Pi
  ни один путь не совпадёт, и индексатор решит, что вся библиотека — новые файлы.
* **`dir` отдельной колонкой с индексом** — чтобы `browse` мог за один запрос достать
  все треки папки: `WHERE dir = ?`. Рекурсивный обход (для «добавить папку в очередь»)
  делается так: `WHERE dir = ? OR substr(dir, 1, length(?) + 1) = ? || '/'`. Это скан
  таблицы, но на 50 тысячах коротких строк это миллисекунды, а с `LIKE`/`GLOB` придётся
  экранировать `%`, `_`, `[` в именах папок — они там бывают (`[2003] Absolution`).
* **Числа хранятся числами.** `utils.get_audio_info` в плеере возвращает строки вида
  `"228.40 сек"` — это формат для показа, в базу такое класть нельзя. Форматирует клиент.
* **`cover_hash` вместо копии обложки на каждый трек.** В альбоме 12 треков — одна и та же
  картинка. Полная обложка бывает 500 КБ — без дедупликации 20 тысяч треков дадут
  10 ГБ дублей. Файл обложки лежит в `covers/<sha1>_full.jpg`, треки ссылаются на него
  по хэшу.
* **`missing` вместо `DELETE`.** Файл может исчезнуть временно — диск не примонтировался,
  папку переименовали и сейчас переименуют обратно. Если удалить строку, `id` потерян,
  и плейлист на плеере сломан. Строка остаётся, `missing = 1`, сервер отвечает на такой
  `id` 410 Gone; физическое удаление — только по явной команде `--purge`.
* **`seen_gen`** — номер поколения скана. Это то, что позволяет найти исчезнувшие файлы
  без второго обхода: всё, у чего `seen_gen < текущий`, на диске не встретилось.

## 3. `tags.py` — чтение одного файла

```python
def read_tags(path: Path) -> dict:
    """
    Возвращает:
      name, author, album, year, genre   -> str | None
      duration                           -> float | None
      sample_rate, bitrate, channels, bits -> int | None
      cover                              -> bytes | None  (оригинальные байты, не сжатые)
    Никогда не бросает исключение наружу: если файл не читается,
    возвращает словарь с name = path.stem и остальными None.
    """
```

Логика уже написана в плеере, её надо перенести, поменяв только формат выхода:

| Что | Откуда брать | Что поменять |
|---|---|---|
| определение формата и разбор тегов | `utils.get_audio_tags` | возвращать `None`, а не `'-'`, для отсутствующих полей |
| fallback на файл с неправильным расширением | `utils.detect_and_load_audio` | как есть |
| тех. данные | `utils.get_audio_info` | сырые числа вместо `f"{...} Гц"` |
| обложка из тегов + `cover.jpg` рядом | `ui_utils.extract_cover` / `possible_covers` | вернуть оригинальные байты, уменьшать будет индексатор |
| fallback названия/автора/альбома по структуре папок | те же функции: `path.stem`, `parent.parent.stem`, `parent.stem` | как есть |

Строки: `strip()`, пустая строка → `None`. Год — оставить `TEXT`, в тегах встречается и
`2003`, и `2003-11-04`, и мусор.

## 4. `indexer.py` — алгоритм скана

```python
def scan(root: Path, conn, *, full: bool = False, batch: int = 200) -> ScanReport
```

### 4.1 Шаги

1. **Защита от пустого диска.** Если `root` не существует, пуст, или в нём нет ни одного
   аудиофайла, а в базе при этом есть треки — **прервать скан, ничего не трогать**,
   записать `last_error`. Это ситуация «HDD не примонтировался»: без этой проверки один
   запуск по пустой точке монтирования пометит всю библиотеку как `missing`.

2. **Взять блокировку.** `meta.scan_running = 1`. Если уже `1` и `scan_started` моложе
   часа — выйти: скан уже идёт. Если старше часа — считать предыдущий упавшим и продолжить.

3. **Новое поколение.** `gen = int(time.time())`, записать в `meta.scan_gen`.

4. **Обход.** `os.scandir` рекурсивно, а не `rglob` — `scandir` отдаёт `stat` одним
   системным вызовом вместе с именем, на HDD это в разы быстрее. Пропускать: скрытые
   папки (имя с `.`), `covers/`, `lost+found`, `$RECYCLE.BIN`, `System Volume Information`.
   Символьные ссылки не разыменовывать (`follow_symlinks=False`) — иначе можно уйти в цикл.

5. **Для каждого файла с расширением из `SUPPORTED_FORMATS`:**
   ```
   rel  = path.relative_to(root).as_posix()
   size = st.st_size ; mtime = int(st.st_mtime)
   row  = SELECT id, size, mtime FROM tracks WHERE rel_path = ?

   нет строки              → read_tags → INSERT (seen_gen = gen)
   есть, size+mtime те же  → UPDATE seen_gen = gen, missing = 0        (файл НЕ читается)
   есть, что-то изменилось → read_tags → UPDATE всех полей, seen_gen = gen
   full = True             → read_tags всегда
   ```
   Ветка «те же» — это то, что делает повторный скан быстрым: по 20 тысячам файлов
   он проходит за секунды, потому что открывает ноль из них.

6. **Обложка**, если `read_tags` вернул байты: `sha1(bytes)`; если `covers/<sha1>_full.jpg`
   ещё нет — сохранить оригинал как JPEG (RGBA/P → RGB, как в `extract_cover_miniature`)
   и миниатюру `_50.jpg` (thumbnail 50×50, quality 85). Записать `cover_hash` в строку.
   Одна и та же обложка на альбом пишется один раз, остальные 11 треков просто ссылаются.

7. **Коммит пачками** по `batch` файлов. Не по одному (каждый commit — это fsync, на
   SD-карте это десятки миллисекунд) и не одной транзакцией на весь скан (база будет
   заблокирована на запись минуты — WAL не спасает от писателя-долгожителя). После
   каждой пачки обновлять `meta.scan_seen`, `meta.scan_parsed` — ping будет показывать
   прогресс.

8. **Переименования.** После обхода: `candidates = SELECT ... WHERE seen_gen < gen AND
   missing = 0` — то, что раньше было, а теперь не нашлось. Для каждого искать строку
   **этого** поколения с теми же `size` и `mtime` (и `duration`, если есть). Нашлась одна —
   это переименование: у старой строки обновить `rel_path`, `dir`, у новой строки —
   удалить. `id` сохраняется, плейлисты на плеере живы. Нашлось ноль или больше одной —
   не гадать, пометить `missing = 1`.

9. **Снять блокировку**, записать `scan_finished`, вернуть отчёт: сколько увидели,
   сколько прочитали, сколько новых, сколько переименовано, сколько пропало, сколько
   ошибок, время.

### 4.2 Что индексатор не делает

* Не транскодирует, не переименовывает, не переносит — **диск только читается**.
* Не удаляет строки без `--purge`.
* Не блокирует сервер: WAL-режим, и сервер держит соединение только на чтение.
* Не делает дедупликацию «одинаковых» треков по тегам.

### 4.3 CLI

```
python indexer.py                # инкрементальный скан
python indexer.py --full         # перечитать теги у всех, даже неизменившихся
python indexer.py --purge        # удалить строки с missing = 1 и обложки без ссылок
python indexer.py --stats        # сколько треков, missing, размер базы, последний скан
```

Из `server.py` вызывается та же `scan()` в фоновом потоке — это и есть `POST /api/rescan`.

## 5. Как эндпоинты используют базу

После появления `library.db` все восемь эндпоинтов становятся одинаково короткими:

| Эндпоинт | Запрос к базе | Диск |
|---|---|---|
| `ping` | `SELECT COUNT(*) FROM tracks WHERE missing = 0` + `meta.scan_*` | нет |
| `browse?path=` | `iterdir()` для папок; для файлов `SELECT id, name, author, duration WHERE dir = ?` | одна папка |
| `search?q=` | `WHERE (name LIKE ? OR author LIKE ? OR album LIKE ?) AND missing = 0 LIMIT ?` | нет |
| `track/{id}` | `SELECT * WHERE id = ?` → 404 нет, 410 missing | нет |
| `tracks?ids=` | `WHERE id IN (...)`, ограничить 500 id | нет |
| `track/{id}/cover` | `SELECT cover_hash WHERE id = ?` → `FileResponse(covers/<hash>_<size>.jpg)` | один файл |
| `stream/{id}` | `SELECT rel_path WHERE id = ?` → `FileResponse(safe_path(rel_path))` | один файл |
| `rescan` | `meta.scan_running` → запуск `scan()` в потоке | весь обход, в фоне |

`browse` — единственный, где диск и база встречаются: структуру папок отдаёт файловая
система (папок в базе нет), треки — база. Клиент получает `type: "folder"` с `uri`
вида `srv://home/d/Rock/Muse` и `type: "track"` с `uri` вида `srv://home/t/48213`.
Файлы, которые на диске есть, а в базе ещё нет (скан не успел) — просто не показывать,
они появятся после скана.

## 7. Порядок работ

1. **`db.py`** — схема из раздела 2, `get_conn()` (с `row_factory = sqlite3.Row`,
   `PRAGMA foreign_keys`, WAL), `init_db()`, проверка `user_version`.
2. **`tags.py`** — `read_tags()`. Проверить на одном mp3, одном flac, одном файле с
   обложкой в тегах, одном с `cover.jpg` рядом, одном с неправильным расширением.
3. **`indexer.py`** — `scan()` + CLI. Прогнать на своей папке `music`, открыть
   `library.db` в DB Browser for SQLite и глазами посмотреть, что легло.
4. Прогнать сценарии из раздела 8.
5. Только теперь — вернуться к `server.py`: переписать `ping`, `browse`, `search` на базу,
   потом добавить остальные пять.

## 8. Проверка индексатора

| Сценарий | Ожидание |
|---|---|
| Первый скан папки с N файлами | N строк, `parsed = N` |
| Повторный скан без изменений | `parsed = 0`, все `seen_gen` обновлены, время в разы меньше первого |
| Поменять теги одного файла (mtime изменится) | `parsed = 1` |
| Переименовать один файл | тот же `id`, новый `rel_path`, `renamed = 1` |
| Переместить файл в другую папку | тот же `id`, новые `rel_path` и `dir` |
| Удалить файл | строка осталась, `missing = 1`; `--purge` удаляет |
| Вернуть удалённый файл на место | `missing = 0`, тот же `id` |
| Указать пустую папку как root при непустой базе | скан прерван, база не тронута, `last_error` заполнен |
| Два файла с одинаковыми `size + mtime` пропали и появились | оба `missing = 1`, а не перепутанные id |
| `.flac`, который на самом деле mp3 | проиндексирован через fallback, `parsed` не упал |
| Файл, который mutagen не читает вообще | строка есть, `name = имя файла`, остальное `NULL`, в отчёте `errors = 1` |
| Скан во время работы сервера | `GET /api/track/1` отвечает, не ждёт конца скана |
| 12 треков одного альбома с одной обложкой | в `covers/` два файла (`_50`, `_full`), не 24 |
| Скан на Windows → перенос `library.db` на Linux → скан | 0 новых, 0 пропавших: `rel_path` совпали |
