# ТЗ: Э5 «Очередь и плейлисты с сервера»

Дополнение к `TZ_streaming.md`. Э0–Э4 закрыты: сервер работает, индексатор работает,
`RemoteSource` отдаёт мету и обложки, проводник ходит по библиотеке Pi.

Формально очередь и плейлисты **уже работают** с серверными треками: `add_queue` и
`add_track_to_playlist` после Э1 вызывают `src.expand` / `src.meta` / `src.cover` и не
знают, локальный источник или сетевой. Этап не про «заставить работать», а про
**сделать это быстро и не морозить интерфейс**.

---

## 5.0 Что именно не так сейчас

`add_queue` (`ui_utils.py:315`) для папки с сервера делает:

```
src.expand(uri)                     1 запрос   -> N URI
для каждого из N:
    src.meta(track_uri)             0 запросов (кэш заполнен из expand)   ✓
    src.cover(track_uri, "50")      1 запрос   <- вот это
```

То есть на альбом из 50 треков уходит **51 HTTP-запрос**, и все они — в UI-потоке.
Интерфейс стоит всё это время. На целой библиотеке (тысячи треков) это минуты
заморозки и гарантированное «приложение не отвечает».

Кэш меты, сделанный на Э3, свою часть уже закрыл: `expand` кладёт в него полные строки,
и `meta` сети не трогает. Осталась обложка — она не помещается в тот же ответ, потому
что это бинарник.

Вторая проблема — **всё это синхронно**. Даже один запрос в UI-потоке подвешивает
отрисовку; пятьдесят подвешивают её заметно.

---

## 5.1 Что делаем

Три независимые задачи, в порядке убывания эффекта:

1. **Обложки при массовом добавлении не тянуть вообще** (см. 5.2).
2. **Длинные операции — в фоновый поток** с индикатором (см. 5.3).
3. **Запись в БД — одной транзакцией**, а не построчно (см. 5.4).

---

## 5.2 Обложки: отложенная загрузка — ✅ СДЕЛАНО

### Идея

При добавлении 50 треков в очередь миниатюры не нужны **в момент добавления** — нужны
в момент, когда строка появится на экране. Пользователь видит первые 10 строк, до
остальных может не долистать никогда.

Поэтому:

* `add_queue` и `add_track_to_playlist` для **серверных** треков пишут в `cov_bytes`
  **NULL** и не делают ни одного запроса за обложкой;
* отрисовка строки (`build_queue_cell`) при `cov_bytes IS NULL` и серверном URI ставит
  иконку-заглушку и ставит трек в **очередь дозагрузки**;
* фоновый поток разбирает эту очередь, тянет обложки по одной, пишет в `queue.db` /
  `app.db` и шлёт в UI сигнал «строка обновилась».

Для **локальных** треков ничего не меняется: чтение обложки с диска быстрое, оставляем
как есть.

### Как сделано

Отдельный модуль `cover_worker.py`:

```python
cover_worker.request_cover(uri)      # «попроси и забудь», ничего не возвращает
cover_worker.start_cover_worker(page)  # поток-демон, запускается рядом со start_server_watch
```

Отличия от первоначального плана, все в лучшую сторону:
* соединения с БД открываются **один раз на поток** и живут, пока он жив — SQLite
  привязан к потоку, переоткрывать на каждую обложку незачем;
* `UPDATE ... WHERE path = ?` обновляет сразу все дубли одного трека в очереди,
  поэтому `uid` строки не нужен;
* множество `no_cover` помнит треки, у которых обложки нет, — иначе каждая
  перерисовка списка снова просила бы то, чего не существует.

Требования:
* очередь — `queue.Queue()`, поток-демон, как `bg_ui_process`;
* один и тот же URI не ставить в очередь дважды (множество «уже в работе»);
* если сервер недоступен — не копить бесконечно: при `server_online() == False`
  очередь чистится, заглушка остаётся;
* после записи в БД — `page.pubsub.send_all_on_topic("cover_ready", {"uid": ..., "cov": ...})`,
  UI обновляет одну строку, а не перерисовывает весь список.

### Результат замера

17 треков с сервера: **0,03 с** на добавление, 0 обложек при вставке, все 17
дотянуты фоновым потоком за несколько секунд.

## 5.3 Фоновое выполнение и индикатор

### Что уводим в поток

| Операция | Где | Почему |
|---|---|---|
| `add_queue` для папки | контекстное меню, drag&drop | N запросов + N вставок |
| `add_track_to_playlist` для папки | то же | то же |
| `list_dir` при смене папки | `open_dir` в `gui2.py` | 1 запрос в UI-потоке — та самая задержка при переключении на «Сервер» |

`add_playlist_to_queue` из списка убрана: оттуда удалён вызов `src.meta` — имя, автор
и обложка уже лежат в `app.db`, перечитывать теги незачем. Функция стала чистой
работой с БД, уводить её в поток не нужно.

Шаблон — тот же, что уже используется в `bg_ui_process`:

```python
def run_bg(page, fn, *args, on_done=None):
    """Выполнить fn в потоке-демоне, по завершении дёрнуть on_done в UI через pubsub."""
```

**Важно:** `sqlite3`-соединение нельзя передавать между потоками. Каждая фоновая
функция открывает своё соединение — в текущем коде так и сделано (`closing(sqlite3.connect(...))`
внутри функции), менять не нужно.

### Индикатор

Пока операция идёт:
* `ft.ProgressRing` или полоска над проводником;
* блокировать повторный запуск той же операции (двойной клик по «Добавить в очередь»
  не должен добавить альбом дважды);
* по завершении — `rebuild_queue_ui()` один раз, а не после каждого трека.

### Критерий

Во время добавления библиотеки целиком интерфейс остаётся отзывчивым: слайдер
двигается, кнопки нажимаются, текущий трек играет без заиканий.

## 5.4 Запись в БД одной транзакцией — отложено

`add_queue` сейчас вставляет по одной строке в цикле, и `commit` один в конце — это уже
правильно. Но `add_track_to_playlist` внутри цикла делает `SELECT id FROM tracks WHERE path = ?`
на каждый трек (`ui_utils.py:~430`), то есть N запросов к SQLite.

Переписать на:
1. один `SELECT id, path FROM tracks WHERE path IN (...)` — получить все существующие;
2. `executemany` для вставки недостающих;
3. один `executemany` для `playlist_tracks`.

На 50 треках разница невелика, на 5000 — секунды против минут. Пока не горит:
после отложенных обложек добавление и так укладывается в сотые доли секунды.

## 5.5 Drag&drop серверных треков

Проверить, что работает (код источник-независимый, но протестировать надо):

* перетаскивание трека из проводника-сервера в очередь — на позицию и в конец;
* перетаскивание папки с сервера в очередь;
* перетаскивание серверного трека в плейлист;
* перестановка серверного трека внутри очереди и внутри плейлиста;
* перетаскивание из очереди в плейлист и обратно.

Отдельно: **перетаскивание серверной папки должно показывать индикатор**, а не
«залипать» на время `expand` + вставки.

## 5.6 Граничные случаи

| Ситуация | Ожидаемое поведение |
|---|---|
| Сервер отвалился посреди добавления альбома | добавленные треки остаются, остальные пропускаются, в логе одна ошибка, не N |
| Добавляем папку, в которой на сервере 0 треков | ничего не добавилось, ошибки нет |
| `expand` вернул 5000 треков | добавляется, интерфейс жив; имеет смысл предупредить диалогом при N > 1000 |
| Один и тот же серверный трек добавлен дважды | в очереди две строки (так же, как для локальных) |
| Трек удалён на сервере (`missing = 1`) | `meta` вернёт 410 → заглушка «сервер недоступен»; лучше отдельный текст «трек удалён» |
| Плейлист со смешанными треками, сервер выключен | локальные играют, серверные пропускаются с сообщением |

---

## 5.7 Критерии приёмки Э5

1. Альбом на 50 треков с сервера добавляется в очередь за < 1 с, интерфейс не замирает.
2. Обложки серверных треков подгружаются сами в течение нескольких секунд.
3. Во время добавления большой папки играющий трек не заикается.
4. Повторный клик по «Добавить в очередь» во время операции не дублирует треки.
5. Drag&drop серверных треков и папок работает во всех шести сценариях из 5.5.
6. Сервер выключен посреди добавления — приложение живо, в очереди то, что успело.
7. Локальное добавление (папка, файл, плейлист) работает ровно как раньше — прогнать
   блок «Очередь» и «Плейлисты» из регрессионного чеклиста.

1. **5.4** — транзакции в `add_track_to_playlist`. Самое простое, не трогает UI.
2. **5.2** — отложенные обложки. Даёт основной выигрыш по скорости.
3. **5.3** — фоновый поток и индикатор. Самое заметное для пользователя.
